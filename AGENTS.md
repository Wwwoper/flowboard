# Инструкции для ИИ-агентов

Проект: **Flowboard** — личный однопользовательский канбан-трекер. Сохраняй его простым, локальным и автономным.

Общие правила работы с Git-репозиторием, проверки базы изменений, подготовки патчей и ZIP-архивов определяются документом `FLOWBOARD_WORK_RULES.md`. Этот файл дополняет общий протокол требованиями, специфичными для Flowboard. При работе соблюдай оба документа. Если общего протокола нет в доступных материалах, запроси его, а не восстанавливай по памяти.

Если просьба пользователя противоречит этим документам, уточни приоритет, когда противоречие влияет на безопасность, сохранность данных или архитектуру. Прямая просьба пользователя не отменяет требований по защите секретов и предотвращению случайной потери данных.

## 1. Как мы работаем

- Flowboard должен оставаться простым, локальным и автономным приложением. Не усложняй архитектуру без обоснованной необходимости.
- Сначала изучай существующую реализацию и используй уже имеющиеся механизмы. Не создавай параллельные способы решения одной задачи.
- Сохраняй совместимость с существующими данными, импортом, экспортом и восстановлением.
- Не изменяй поведение, не относящееся к задаче.
- Не выдумывай существующие функции, настройки, ограничения и структуру проекта. Проверяй их по актуальному коду.
- Согласованные с пользователем функциональные и UI-решения считай требованиями. Не задавай повторно вопросы, на которые уже получен ответ.
- Спецификации отдельных функций храни отдельно, например в `docs/`. Не перегружай этот файл подробностями конкретных функций.

## 2. Архитектура Flowboard

Ниже перечислены известные компоненты проекта. Перед использованием этих сведений в конкретной задаче сверяй их с актуальным деревом репозитория и содержимым файлов. Этот список не заменяет анализ текущего кода.

- `pyproject.toml` — метаданные проекта, зависимости и настройки инструментов; проверяй актуальное содержимое.
- `README` — документация по запуску и использованию; фактическое имя файла и инструкции проверяй в репозитории.
- `docs/` — документация и спецификации отдельных функций, если каталог присутствует.
- `app/main.py` — FastAPI и HTTP API: задачи, вложения, импорт/экспорт, Markdown preview.
- `app/db.py` — подключения и схема SQLite.
- `app/models.py` — модели запросов/ответов и валидация Pydantic.
- `app/importer.py`, `app/exporter.py`, `app/restore.py` — импорт Markdown, экспорт Markdown/ZIP, восстановление архива.
- `app/config.py` — настройки из переменных окружения.
- `app/static/index.html`, `app.js`, `style.css` — интерфейс без сборщика.
- `app/static/dragdrop.js` — локальный адаптер drag-and-drop.
- `tests/` — тесты API, импорта/экспорта, вложений и ключевого поведения фронтенда.
- `data/` — локальные пользовательские данные; в Git ничего, кроме `.gitkeep`.

Python 3.12+. Зависимости и команды — через `uv`. Фронтенд — обычный JS/CSS, без сборщика, внешних CDN и обязательной сети. Эти сведения необходимо подтвердить по актуальным `pyproject.toml`, README, конфигурации и дереву файлов перед изменениями.

## 3. Правила разработки Flowboard

### 3.1. Общие требования

- Делай небольшие целевые изменения: сначала найди существующий путь выполнения и связанные тесты; соседний код без необходимости не переписывай.
- Предпочитай минимальное изменение существующей архитектуры.
- Перед добавлением новой модели, таблицы, API, UI-компонента или зависимости проверь, можно ли использовать существующие механизмы.
- Не дублируй бизнес-логику между API, интерфейсом и фоновыми операциями. У каждого правила должен быть единый источник истины.
- Для новых сущностей явно определяй жизненный цикл, допустимые состояния и переходы между ними.
- Учитывай влияние изменений связанных сущностей на автоматические переходы состояния.
- Проверяй связанные сценарии импорта, экспорта, восстановления и удаления данных, если новая функциональность влияет на соответствующие сущности.

### 3.2. База данных и конфигурация

- База лежит в `TRACKER_DATA_DIR` (по умолчанию `./data`), вложения хранятся отдельно от строк задач. Перед использованием имени настройки и значения по умолчанию обязательно сверь их с актуальным `app/config.py`; не угадывай.
- Сохраняй совместимость данных и экспортов.
- Перед изменением схемы SQLite определи стратегию миграции для существующей базы и добавь тест миграции.
- Не удаляй, не очищай и не перезаписывай пользовательские данные.
- Тесты не должны использовать реальную базу из `data/`: фикстура должна задавать временный каталог.
- Для экспериментов, миграций и тестирования используй временные каталоги и копии данных, а не оригинальную пользовательскую базу.

### 3.3. Задачи, статусы и поля

- Статусы задач: `todo`, `doing`, `waiting`, `done`.
- Лимиты: заголовок до 200 символов, описание до 5000, теги до 1000.
- Точные лимиты и имя настройки ограничения размера файла определяй по актуальному коду, прежде всего `app/config.py`. Не фиксируй их по памяти и не угадывай.
- При изменении валидации обновляй соответствующие тесты и проверяй граничные значения.

### 3.4. Теги и проекты

- Теги хранятся строкой через запятую.
- Проект — представление на основе тега `project:<slug>`.
- Slug соответствует `^[a-z0-9]+(?:-[a-z0-9]+)*$`.
- Не добавляй отдельную сущность проекта в БД без обоснования и плана миграции.
- При изменении обработки тегов проверяй совместимость существующих задач, фильтров, поиска, импорта и экспорта.

### 3.5. Поиск

- Поиск нормализует регистр и `ё`/`е`.
- Каждый токен запроса должен совпасть с текстом.
- При изменении логики поиска покрывай тестами обычные случаи, пустые значения, несколько токенов и граничные случаи.

## 4. Пользовательский интерфейс

### 4.1. Общие принципы

- Сохраняй существующий визуальный стиль и структуру интерфейса.
- Не добавляй элементы управления и сводки, которые не помогают выполнить пользовательскую задачу.
- Не дублируй название задачи в превью описания без необходимости.
- Не искажай Markdown в превью.
- Карточка задачи должна сохранять согласованный порядок информации: название, превью описания, проект, тип, теги и служебные данные.
- Не перегружай правый верхний угол доски сводными счётчиками задач: счётчики должны оставаться в заголовках колонок.
- Сворачивание колонки выполненных задач использует стрелку-chevron без счётчика скрытых карточек и располагается в согласованном месте.
- Если UI-решение неоднозначно, сначала предложи рекомендацию и дождись согласования. Не спрашивай повторно, если решение уже принято.

### 4.2. Состояние интерфейса и ошибки

- Новые действия UI должны корректно обрабатывать HTTP-ошибки и сетевые сбои.
- После успешной мутации интерфейс должен обновляться в соответствии с серверным состоянием.
- Не оставляй старые или несогласованные данные в панели задачи.
- При ошибке показывай пользователю понятное сообщение.
- Не оставляй интерфейс в бесконечном состоянии загрузки.
- При ошибке сохранения корректно восстанавливай или сохраняй состояние интерфейса в соответствии с существующей архитектурой.
- Изменения сохранения данных требуют регрессионных тестов.

### 4.3. Сетевые запросы

Все асинхронные запросы `fetch` должны:

- проверять `response.ok` до обработки успешного ответа;
- обрабатывать сетевые ошибки и исключения;
- показывать пользователю понятное сообщение при неудаче, а не ограничиваться `console.log`;
- корректно восстанавливать или сохранять состояние интерфейса после ошибки;
- не оставлять интерфейс в бесконечном состоянии загрузки.

Не считай HTTP-ответ успешным только потому, что вызов `fetch` завершился без исключения.

### 4.4. Drag-and-drop

При изменении `dragdrop.js`, логики карточек или порядка задач проверяй:

- корректность начала, перемещения и завершения drag-and-drop;
- правильность целевой колонки и позиции карточки;
- сохранение нового порядка на сервере;
- восстановление порядка после перезагрузки;
- поведение при отмене перетаскивания;
- поведение при ошибке сохранения;
- отсутствие повторной регистрации обработчиков событий;
- отсутствие дублирования событий и утечек обработчиков DOM.

Не допускай ситуации, когда визуальный порядок карточек расходится с сохранённым серверным порядком.

### 4.5. Безопасность фронтенда

- Не добавляй фронтенд-зависимости и CDN без явной необходимости.
- Используй DOM API и безопасный вывод данных.
- Markdown preview проходит через существующую серверную очистку.
- Не вставляй пользовательские данные в HTML небезопасным способом.
- Не ослабляй серверную очистку Markdown ради визуального эффекта.
- Не добавляй `console.log`, `debugger` и временные закомментированные блоки в итоговый фронтенд-код.
- Не удаляй обоснованное логирование ошибок, если оно является частью принятого механизма диагностики.

### 4.6. Версионирование статических ресурсов

- При изменении `app.js`, `style.css` или `index.html` обнови версии query-параметров статики в `index.html` в соответствии с существующим в проекте форматом версионирования.
- Сначала изучи текущие ссылки и правила кэширования; не вводи новый формат версии без необходимости.
- Убедись, что все изменённые статические ресурсы получают актуальные версии и браузер не продолжает использовать устаревший кэш.
- Включи проверку этого требования в тест или в проверяемый diff, если в проекте нет автоматического теста.

## 5. Безопасность и локальный режим

- Не ослабляй безопасность ради удобства тестов.
- Встроенной авторизации нет; по умолчанию доступ только на `127.0.0.1`, удалённый доступ — через внешнюю авторизацию и защищённый reverse proxy. Перед применением этих сведений проверь актуальную конфигурацию.
- Не добавляй секреты, токены, ключи, пароли и `.env` в Git.
- Не добавляй в Git SQLite-базы, вложения, бэкапы и личные данные.
- Не открывай и не пересказывай содержимое `data/`, если задача явно этого не требует.
- В ZIP-восстановлении сохраняй защитные проверки путей и перезаписи; не извлекай пути без проверки.
- Для тестирования и миграций используй временные каталоги и копии данных.
