# Инструкции для ИИ-агентов

## Цель проекта

Flowboard — личный однопользовательский канбан-трекер. Сохраняй его простым, локальным и автономным. Перед изменениями прочитай этот файл и соответствующие разделы `README.md`, затем изучи реализацию и тесты затрагиваемого поведения.

## Архитектура

- `app/main.py` — приложение FastAPI и HTTP API: задачи, вложения, импорт/экспорт и Markdown preview.
- `app/db.py` — подключения и схема SQLite.
- `app/models.py` — модели запросов/ответов и валидация Pydantic.
- `app/importer.py`, `app/exporter.py`, `app/restore.py` — импорт Markdown, экспорт Markdown/ZIP и восстановление архива.
- `app/config.py` — настройки из переменных окружения.
- `app/static/index.html`, `app/static/app.js`, `app/static/style.css` — интерфейс без фронтенд-сборщика.
- `app/static/dragdrop.js` — локальный адаптер drag-and-drop.
- `tests/` — тесты API, импорта/экспорта, вложений и ключевого фронтенд-поведения.
- `data/` — локальные пользовательские данные; содержимое, кроме `.gitkeep`, не должно попадать в Git.

Python — 3.12+. Используй `uv` для зависимостей и команд. Фронтенд реализован обычным JavaScript/CSS и должен работать без Node-сборщика, внешних CDN и обязательного сетевого доступа.

## Правила разработки

1. Делай небольшие, целевые изменения. Сначала найди существующий путь выполнения и связанные тесты; не переписывай соседний код без необходимости.
2. Сохраняй совместимость существующих данных и экспортов. База находится в `TRACKER_DATA_DIR` (по умолчанию `./data`); вложения хранятся отдельно от строк задач. Перед изменением схемы SQLite определи стратегию миграции для уже существующей `tracker.db` и добавь тест миграции.
3. Не удаляй, не очищай и не перезаписывай пользовательские данные. Не используй настоящую базу из `data/` для тестов: тестовая фикстура настраивает временный каталог.
4. Статусы задач ограничены значениями `todo`, `doing`, `waiting`, `done`. Сохраняй текущую валидацию и ограничения размеров: заголовок до 200 символов, описание до 5000, теги до 1000; лимит файла задаётся настройкой.
5. Теги хранятся строкой через запятую. Проект — представление на основе тега `project:<slug>`, где slug соответствует `^[a-z0-9]+(?:-[a-z0-9]+)*$`; не добавляй сущность проекта в базу без отдельного обоснования и миграционного плана.
6. Поиск в интерфейсе нормализует регистр и `ё`/`е`; каждый токен запроса должен совпадать с искомым текстом. При изменении логики поиска покрывай крайние случаи тестами.
7. Новые действия интерфейса должны корректно обрабатывать HTTP-ошибки, обновлять UI после успешной мутации и не оставлять старые данные в панели задачи. Изменения, влияющие на сохранение данных, должны иметь регрессионные тесты.
8. Не добавляй фронтенд-зависимости или CDN без явной необходимости: автономность и простой запуск — часть замысла проекта. Используй DOM API и безопасный вывод пользовательских данных; Markdown preview должен проходить через существующую серверную очистку.
9. При изменении `app.js`, `style.css` или `index.html` проверь версии query-параметров статических ресурсов в `index.html`, чтобы браузер получил новые файлы после обновления.
10. Не ослабляй ограничения безопасности для удобства тестирования. Приложение не имеет встроенной авторизации и по умолчанию должно оставаться доступным только на `127.0.0.1`; удалённый доступ требует внешней авторизации и защищённого reverse proxy.

## Проверки

Из корня репозитория запускай:

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
node --check app/static/app.js
node --check app/static/dragdrop.js
```

Если инструмент для отдельной проверки недоступен, явно укажи это в итоговом сообщении. Не заявляй об успешно пройденной проверке, которую фактически не запускал. После исправления ошибок повтори соответствующую проверку.

## Git и передача изменений

- Не смешивай независимые изменения в одном коммите; сообщения коммитов краткие и на английском, в повелительной форме, например `Document undo behavior`.
- Перед коммитом проверь `git diff --check`, тесты и `git status`.
- Для изменений, которые пользователь должен перенести в свой репозиторий, подготовь отдельный patch-файл через `git format-patch -1 --stdout HEAD > /path/to/change.patch`. Проверь применимость на чистом worktree от родительского коммита (`git worktree add --detach ... HEAD^`, затем `git am ...`) и повторно выполни применимые проверки там.
- В итоговом сообщении перечисли изменённые файлы, фактические результаты проверок и путь к patch-файлу. Не выдавай неподтверждённые результаты за проверенные.

## Обращение с секретами и данными

- Не добавляй в Git `.env`, базу SQLite, вложения, резервные копии, пароли, токены или личные данные.
- Не открывай и не пересказывай содержимое пользовательских данных из `data/`, если задача явно этого не требует.
- При работе с ZIP-восстановлением сохраняй существующие защитные проверки пути и перезаписи; не извлекай архивные пути без проверки.
