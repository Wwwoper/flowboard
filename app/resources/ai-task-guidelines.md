# Регламент формирования групп задач для Flowboard

**Версия:** 1.0  
**Назначение:** единый стандарт подготовки групп задач для последующего импорта в Flowboard.  
**Формат результата:** Markdown (`.md`) с YAML Front Matter.  
**Язык задач:** русский, если пользователь не указал другой язык.

## 1. Основная задача

Располагай задачи в Markdown-файле в строгом порядке их предполагаемого выполнения. Порядок блоков является значимым и должен отражать последовательность реализации от первой задачи к последней. ИИ-модель должна преобразовать описание функциональности, идеи, требования или технического задания в структурированную группу независимых задач, готовую к импорту в Flowboard.

Результат должен представлять собой один Markdown-файл, содержащий:
- Общую информацию о группе задач.
- Последовательность логически связанных задач.
- Чёткие названия задач.
- Подробные описания ожидаемых изменений.
- Критерии приёмки.
- Зависимости между задачами.
- Проектные и классификационные теги.

Каждая задача должна быть самостоятельной единицей работы, которую можно выполнять, проверять и принимать отдельно.

## 2. Формат файла

Использовать расширение `.md`.

Для группы задач обязательно применять специальный формат экспорта Flowboard:

1. В начале файла располагается YAML Front Matter с параметром `kanban_export: true`.
2. Каждая задача оформляется отдельным блоком.
3. Блок задачи начинается с `<!-- kanban-task-start -->`.
4. Метаданные задачи располагаются в YAML Front Matter.
5. После метаданных располагается Markdown-описание задачи.
6. Блок заканчивается `<!-- kanban-task-end -->`.

Структура:

```markdown
---
kanban_export: true
---

# Название группы задач

<!-- kanban-task-start -->
---
title: Название задачи
status: todo
tags:
  - project:имя-проекта
  - backend
task_type: feature
result: ""
---
Описание задачи в Markdown.

<!-- kanban-task-end -->
```

Повторять блок для каждой следующей задачи.

**Важно:** нельзя заменять этот формат произвольным Markdown-списком, таблицей задач или YAML-массивом. Импортер Flowboard должен распознавать отдельные блоки задач.

## 3. Метаданные задачи

Для каждой задачи использовать следующие поля.

### 3.1. Обязательное поле

`title` — краткое название задачи.

Требования:
- Максимум 200 символов.
- Формулировка должна описывать конкретное действие или результат.
- Не использовать общие названия вроде «Улучшить приложение», «Доработать интерфейс», «Исправить ошибки».
- Предпочитать формулировки с конкретным объектом изменения.

Хорошо:
- «Добавить фильтрацию задач по нескольким тегам».
- «Исправить восстановление порядка карточек после перезагрузки».
- «Добавить проверку совместимости Markdown-экспорта».

Плохо:
- «Работа с тегами».
- «Улучшения».
- «Проверить приложение».

### 3.2. Статус

Поле `status`.

Допустимые значения:

| Значение | Назначение |
|---|---|
| `todo` | К выполнению |
| `doing` | В работе |
| `waiting` | Ожидает |
| `done` | Готово |

Для всех новых задач использовать:

```yaml
status: todo
```

Не назначать задачи выполненными или находящимися в работе без прямого указания пользователя.

### 3.3. Тип задачи

Поле `task_type`.

Допустимые значения:

| Значение | Назначение |
|---|---|
| `bug` | Исправление ошибки |
| `feature` | Новая функциональность |
| `docs` | Документация |
| `refactor` | Рефакторинг |

Если задача не относится однозначно ни к одному типу, использовать пустое значение:

```yaml
task_type: ""
```

Не придумывать дополнительные типы.

### 3.4. Теги

Поле `tags` — YAML-список.

Пример:

```yaml
tags:
  - project:flowboard
  - backend
  - api
  - validation
```

Правила:

- Каждая задача обязательно получает тег проекта, если задача относится к конкретному проекту.
- Формат проектного тега: `project:<slug>`.
- Slug должен соответствовать шаблону `^[a-z0-9]+(?:-[a-z0-9]+)*$`.
- Дополнительные теги обозначают функциональную область, компонент или технологию.
- Использовать короткие и понятные названия.
- Не создавать десятки уникальных тегов.
- Не использовать названия встроенных типов задач в качестве обычных тегов.

Рекомендуемые категории тегов:

- `backend`
- `frontend`
- `api`
- `database`
- `ui`
- `ux`
- `testing`
- `security`
- `import-export`
- `performance`
- `documentation`

Список тегов должен соответствовать реальному содержанию задачи.

### 3.5. Результат выполнения

Поле `result`:

```yaml
result: ""
```

Для новых задач оставлять пустым.

Не записывать сюда ожидаемый результат реализации. Ожидаемый результат должен находиться в описании задачи.

## 4. Структура описания задачи

Описание должно быть достаточно подробным, чтобы разработчик мог приступить к работе без повторного изучения исходного запроса пользователя.

Рекомендуемая структура:

```markdown
## Цель

Что необходимо реализовать и какую проблему это решает.

## Контекст

Описание существующей ситуации, ограничений и причин изменения.

## Требования

- Конкретное требование 1.
- Конкретное требование 2.
- Конкретное требование 3.

## Логика реализации

Подробное описание ожидаемого поведения системы.

## Критерии приёмки

- [ ] Критерий 1.
- [ ] Критерий 2.
- [ ] Критерий 3.

## Проверки

- Проверить основной сценарий.
- Проверить граничные случаи.
- Проверить отсутствие регрессий.
```

Разделы можно адаптировать к типу задачи.

Не нужно механически добавлять разделы, которые не имеют смысла для конкретной работы.

## 5. Правила декомпозиции

ИИ-модель обязана самостоятельно разделить исходное описание на логические задачи.

### 5.1. Общие правила

- Одна задача — один логический результат.
- Задача должна иметь понятные границы выполнения.
- Задача должна иметь проверяемые критерии приёмки.
- Не объединять независимые изменения только ради сокращения количества задач.
- Не дробить простую задачу на искусственные подзадачи.
- Не создавать задачи, которые не приводят к самостоятельному результату.
- Не дублировать одинаковые требования в нескольких задачах без необходимости.

### 5.2. Рекомендуемый порядок

Если исходное описание содержит функциональность, затрагивающую несколько компонентов, использовать следующую последовательность:

1. Анализ существующей реализации и определение архитектурных ограничений.
2. Подготовка моделей данных и необходимых изменений схемы.
3. Реализация серверной логики и API.
4. Реализация пользовательского интерфейса.
5. Добавление и обновление автоматических тестов.
6. Интеграционная проверка.
7. Обновление документации.

Это рекомендуемый порядок, а не обязательная последовательность для любой задачи.

Объединять этапы разрешается, если изменения небольшие и логически неделимые.

### 5.3. Размер задачи

Предпочтительно формировать задачи, которые:
- Имеют ограниченную область изменений.
- Могут быть реализованы без одновременного изменения большого количества несвязанных компонентов.
- Имеют понятный результат.
- Могут быть проверены отдельно.

Не устанавливать искусственные ограничения по количеству задач или строк кода.

## 6. Зависимости между задачами

Если выполнение одной задачи требует предварительного выполнения другой, явно указывать зависимость в описании.

Пример:

```markdown
## Зависимости

- Требует выполнения задачи: «Добавить серверную поддержку нового поля».
- После выполнения может начинаться задача: «Добавить отображение нового поля в интерфейсе».
```

Не создавать отдельные фиктивные задачи только для обозначения зависимостей.

Если задачи независимы, не указывать зависимости.

Порядок блоков в файле должен соответствовать рекомендуемой последовательности выполнения.

## 7. Требования к качеству постановки

Каждая задача должна отвечать на следующие вопросы:

1. Что необходимо изменить?
2. Почему это необходимо?
3. Какое поведение ожидается?
4. Какие компоненты могут быть затронуты?
5. Как определить, что работа завершена?
6. Какие проверки необходимо выполнить?

Необходимо избегать:
- Неоднозначных формулировок.
- Общих пожеланий вместо требований.
- Предположений, представленных как факты.
- Необоснованного выбора архитектуры.
- Навязывания конкретной реализации без необходимости.
- Противоречивых требований.
- Повторяющихся задач.
- Отсутствия критериев приёмки.

Если исходное описание недостаточно для однозначной постановки, сначала обозначить неопределённость и запросить необходимые сведения либо явно зафиксировать допущение.

## 8. Особенности проекта Flowboard

При подготовке задач для Flowboard соблюдать следующие ограничения:

- Приложение должно оставаться простым, локальным и автономным.
- Предпочитать существующую архитектуру и механизмы.
- Не предлагать новые зависимости без обоснования.
- Сохранять совместимость с существующими данными.
- Учитывать импорт, экспорт и восстановление данных.
- Для изменений SQLite предусматривать миграции.
- Для изменений бизнес-логики предусматривать автоматические тесты.
- Для UI учитывать существующий дизайн-системный контракт.
- Для асинхронных запросов учитывать обработку HTTP-ошибок и сетевых сбоев.
- Не включать в задачи несвязанный рефакторинг.

При постановке задачи не считать, что существующая реализация соответствует документации: фактическое состояние необходимо проверять по актуальному репозиторию.

## 9. Технические ограничения формата импорта

При подготовке Markdown-файла соблюдать ограничения текущего импортера:

| Параметр | Ограничение |
|---|---|
| Формат файла | `.md` |
| Кодировка | UTF-8 |
| Максимальная длина заголовка | 200 символов |
| Максимальная длина описания | 30 000 символов |
| Максимальная длина результата | 30 000 символов |
| Статус | `todo`, `doing`, `waiting`, `done` |
| Тип | `bug`, `feature`, `docs`, `refactor` |
| Группировка | `kanban_export: true` и отдельные блоки задач |

Дополнительные правила:

- Для каждой задачи обязательно указывать непустой `title`.
- YAML должен быть корректным.
- Для русскоязычных значений использовать кавычки при необходимости.
- Не включать произвольные дополнительные поля в расчёте на их сохранение.
- Даты создания и изменения не указывать, если они не нужны для специального сценария переноса.
- Вложения не включать в обычный Markdown-файл. Для переноса вложений использовать отдельный поддерживаемый ZIP-формат задачи.
- Не рассчитывать на автоматическое распознавание зависимостей: они остаются частью текстового описания.

Не использовать несуществующие поля `project`, `priority`, `assignee`, `estimate`, `parent_id` и другие неподдерживаемые поля. Проект задаётся тегом `project:<slug>`.

## 10. Проверка перед выдачей результата

Перед передачей файла пользователю ИИ-модель обязана выполнить контрольный список.

### Структура

- [ ] Файл имеет расширение `.md`.
- [ ] Кодировка UTF-8.
- [ ] В начале присутствует `kanban_export: true`.
- [ ] Каждая задача имеет собственный блок.
- [ ] Каждый блок начинается с `<!-- kanban-task-start -->`.
- [ ] Каждый блок заканчивается `<!-- kanban-task-end -->`.
- [ ] Между маркерами присутствует корректный YAML Front Matter.

### Содержание

- [ ] У каждой задачи есть непустой заголовок.
- [ ] Заголовки конкретны и понятны.
- [ ] Все задачи имеют статус `todo`, если не указано иное.
- [ ] Все задачи имеют корректный тип или пустой тип.
- [ ] Теги соответствуют содержанию.
- [ ] Проектный тег указан там, где он необходим.
- [ ] Нет дублирующихся задач.
- [ ] Нет противоречивых требований.
- [ ] Критерии приёмки проверяемы.
- [ ] Зависимости обозначены, если они существуют.

### Результат

- [ ] Все задачи находятся в одном Markdown-файле.
- [ ] Количество задач соответствует результату декомпозиции.
- [ ] Порядок задач отражает рекомендуемую последовательность.
- [ ] Файл не содержит пояснений для пользователя вне формата задач.

## 11. Формат ответа ИИ-модели

После подготовки группы задач ИИ-модель должна предоставить:

1. Краткое название группы.
2. Краткое объяснение принципа декомпозиции.
3. Количество сформированных задач.
4. Сам Markdown-файл, готовый к импорту.

Если модель может создавать файлы, необходимо приложить готовый `.md`.

Если создание файлов недоступно, вывести полный Markdown в одном отдельном кодовом блоке.

Не выдавать вместо готового файла описание того, как пользователь может самостоятельно сформировать задачи.

Не включать в импортируемый файл дополнительные инструкции, отчёты или пояснения, не относящиеся к задачам.

**Главное требование:** результат должен быть непосредственно пригоден для импорта через Flowboard без ручного исправления структуры и метаданных.
