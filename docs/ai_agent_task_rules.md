# Правила для ИИ-агента: формирование задач в Flowboard

## Цель

Преобразуй запрос пользователя в короткую, понятную карточку — сообщение об ошибке, запрос на доработку, документацию или рефакторинг. Карточка фиксирует **что не так или какой результат нужен**, а не содержит полное техническое задание и рассуждения агента.

## 1. Формат карточки

Для каждой задачи подготовь:

- **Заголовок:** конкретное действие и один результат; ориентир 5–12 слов.
- **Тип:** одно отдельное поле (`bug`, `feature`, `docs`, `refactor`).
- **Теги:** ровно один `project:<slug>`. При реальной необходимости допустимы 1–2 тега области.
- **Описание:** обычно 30–70 слов, 2–5 коротких строк. Не растягивай описание ради соблюдения объёма, если достаточно меньшего текста.
- **Статус:** `todo`, если пользователь не указал другой.

Не добавляй префиксы `[BUG]` и `[FEATURE]` в заголовок: тип хранится в отдельном поле.

## 2. Теги

### Проект

Формат `project:<slug>`: строчные латинские буквы, цифры и дефисы, без пробелов. Используй согласованный slug и не создавай альтернативные названия одного проекта.

Известные примеры:

- `project:storefront`
- `project:rope-knots`
- `project:template-menu`
- `project:kanban-tracker`

Если проект нельзя уверенно определить из текущего запроса и контекста, задай один короткий уточняющий вопрос. Не угадывай.

### Тип

Выбери ровно один и передай его в отдельном поле типа, не в списке тегов:

- `bug` — наблюдаемое неправильное поведение существующей функции;
- `feature` — новая возможность или изменение поведения;
- `docs` — документация, инструкции или поясняющие тексты;
- `refactor` — внутренняя перестройка без изменения поведения пользователя.

Дополнительные теги (`frontend`, `backend`, `tests`, `ux`) добавляй только если они помогают фильтровать работу. Не добавляй обозначение типа в виде префикса заголовка.

## 3. Шаблоны описания

Используй только подходящий шаблон. Не заполняй отсутствующие сведения догадками и не добавляй пустые поля.

### Ошибка — `bug`

```text
Проблема: кратко опиши фактическое поведение.
Ожидалось: укажи правильное поведение.
Проверка: один способ проверить исправление. (если полезно)
```

### Доработка — `feature`

```text
Нужно: опиши требуемое изменение.
Готово, когда:
- проверяемое условие 1;
- проверяемое условие 2. (если необходимо)
```

### Документация — `docs`

```text
Обновить: конкретный документ или раздел.
Включить: 1–3 обязательных пункта.
```

### Рефакторинг — `refactor`

```text
Область: модуль или компонент.
Изменить: внутреннее упрощение или разделение ответственности.
Сохранить: важное поведение и совместимость.
```

## 4. Правила качества

1. **Одна карточка — один самостоятельный результат.** Разделяй независимые ошибки, функции и изменения документации.
2. Заголовок должен быть понятен без чтения описания. Предпочитай глагол действия и конкретный объект.
3. Указывай 1–3 проверяемых критерия готовности, если они помогают принять результат. Не добавляй формальные критерии вроде «работает корректно».
4. Описывай только подтверждённые факты. Не выдумывай причину ошибки, шаги воспроизведения, ожидаемое поведение, сроки или ограничения.
5. Не включай длинную предысторию, анализ агента, подробный план реализации, список несвязанных улучшений или полное архитектурное решение.
6. Не смешивай исправление и независимый рефакторинг в одной задаче.
7. Не добавляй исполнителей, приоритеты, сроки и подзадачи: формат текущей доски этого не предусматривает.
8. Если не хватает критического факта, который меняет смысл задачи, задай один короткий вопрос. Если уточнение необязательно, не перегружай карточку.
9. Не повторяй в описании сведения, уже однозначно переданные заголовком или тегами.

## 5. Markdown для импорта

Если пользователь просит файл для импорта, подготовь **один `.md`-файл на одну задачу** с YAML frontmatter. Теги передавай списком строк, чтобы `project:<slug>` разбирался однозначно.

```markdown
---
title: Исправить сброс фильтра после обновления
status: todo
tags: ["project:kanban-tracker"]
task_type: bug
---
Проблема: выбранный тег сбрасывается после обновления страницы.
Ожидалось: выбранный фильтр остаётся активным.
Проверка: выбрать тег и перезагрузить страницу.
```

Не объединяй несколько обычных frontmatter-блоков в один файл: стандартный импорт создаёт одну задачу на файл. Импорт не ищет дубликаты и не обновляет существующие карточки.

## 6. Примеры

### Хорошо — ошибка

- **Заголовок:** `Исправить потерю порядка карточек после обновления`
- **Тип:** `bug`
- **Теги:** `project:kanban-tracker`
- **Описание:** `Проблема: после перезагрузки карточки возвращаются в прежнем порядке. Ожидалось: сохранённый порядок остаётся после обновления страницы. Проверка: изменить порядок и перезагрузить страницу.`

### Хорошо — доработка документации

- **Заголовок:** `Добавить ссылку на инструкцию восстановления`
- **Тип:** `docs`
- **Теги:** `project:kanban-tracker`
- **Описание:** `Обновить: раздел резервного копирования в README. Включить: команду восстановления, пример отдельного каталога и предупреждение о перезаписи данных.`

### Плохо

`Срочно полностью переработать управление проектом, изучить архитектуру, улучшить интерфейс и добавить все нужные функции.`

Причина: смешано несколько независимых результатов, нет проверяемого ожидания и невозможно однозначно принять работу.

## 7. Формат ответа

Когда пользователь просит **сформировать задачу**, по умолчанию верни только карточку:

```text
Заголовок: ...
Тип: <bug|feature|docs|refactor>
Теги: project:<slug>
Статус: todo
Описание:
...
```

Если пользователь просит импортируемый файл, верни содержимое одного `.md` с frontmatter. Если требуется несколько задач, раздели их на отдельные карточки или файлы. Не добавляй длинных пояснений до или после результата, если пользователь их не просил.

Если пользователь просит не создать карточку, а обсудить или уточнить задачу, отвечай в обычном формате и не выдавай текст за готовую карточку.
