# Правила для ИИ-агента: как оформлять задачи для Flowboard

## Цель

Создавай короткие карточки в стиле отчёта об ошибке, исправлении или доработке. Задача должна объяснять **что не так или какой результат нужен**, а не превращаться в техническое задание на несколько страниц.

## 1. Обязательные поля

Для каждой задачи подготовь:

- **Заголовок** — одно действие и один результат; ориентир 5–12 слов. Формулируй конкретно, без общих слов «улучшить всё», «разобраться» или «починить приложение».
- **Теги** — ровно один тег проекта и один тег типа.
- **Описание** — обычно 2–5 коротких строк, ориентир 30–70 слов. Добавляй только сведения, необходимые для понимания и проверки задачи.
- **Статус** — по умолчанию `todo`, если пользователь явно не указал другое.

### Тег проекта

Формат: `project:<slug>` — строчные латинские буквы, цифры и дефисы, без пробелов. Используй согласованный тег проекта, не создавай для того же проекта альтернативные названия.

Примеры: `project:storefront`, `project:rope-knots`, `project:template-menu`, `project:kanban-tracker`.

Если проект определить нельзя, не угадывай — задай один короткий уточняющий вопрос.

### Тег типа

Выбери ровно один:

- `bug` — наблюдаемое неправильное поведение;
- `feature` — новая возможность или изменение поведения;
- `docs` — документация или инструкции;
- `refactor` — изменение внутренней структуры без изменения внешнего поведения.

При реальной необходимости разрешены 1–2 дополнительных тега области (`backend`, `frontend`, `tests`, `ux`). Не добавляй их автоматически. Тип задачи хранится в теге, поэтому обычно не нужно дублировать его в заголовке префиксами `[BUG]` или `[FEATURE]`.

## 2. Как писать описание

Выбирай только подходящий шаблон. Не заполняй разделы искусственно, если информации для них нет.

**Ошибка (`bug`)**

```text
Проблема: кратко опиши фактическое поведение.
Ожидалось: укажи правильное поведение.
Проверка: 1 короткий способ проверить исправление. (если полезно)
```

**Доработка (`feature`)**

```text
Нужно: опиши требуемое изменение.
Готово, когда:
- проверяемое условие 1;
- проверяемое условие 2. (если необходимо)
```

**Документация (`docs`)**

```text
Обновить: укажи конкретный документ или раздел.
Включить: перечисли 1–3 обязательных пункта.
```

**Рефакторинг (`refactor`)**

```text
Область: укажи модуль или компонент.
Изменить: опиши внутреннее упрощение.
Сохранить: важное поведение или совместимость, которые нельзя нарушить.
```

## 3. Ограничения объёма и качества

1. Одна карточка — один самостоятельный результат. Разделяй независимые ошибки, функции и документационные задачи.
2. Заголовок должен быть понятен без чтения длинного описания.
3. Используй 1–3 проверяемых критерия готовности, только когда они помогают понять результат.
4. Не включай длинную предысторию, повтор исходного сообщения, рассуждения агента, план по шагам, полный дизайн решения или список всех возможных улучшений.
5. Не выдумывай шаги воспроизведения, причины ошибки, ограничения и ожидаемое поведение. Если критического факта не хватает, задай вопрос; если уточнение необязательно, оставь его за пределами задачи.
6. Не смешивай исправление ошибки и отдельный рефакторинг в одной карточке, если их можно выполнить и принять независимо.
7. Не добавляй сроки, исполнителей, приоритеты и подзадачи: текущий трекер этого не поддерживает.

## 4. Формат для импорта в Flowboard

Для импорта используй Markdown с YAML frontmatter: **один файл `.md` — одна задача**. Теги передавай списком строк, чтобы двоеточие в `project:<slug>` было однозначным.

```markdown
---
title: Исправить сброс фильтра после обновления
status: todo
tags: ["project:kanban-tracker", "bug"]
---
Проблема: выбранный тег сбрасывается после обновления страницы.
Ожидалось: активный фильтр сохраняется в пределах текущего состояния интерфейса.
Проверка: выбрать тег, обновить страницу и проверить поведение.
```

Для нескольких задач подготовь отдельный `.md`-файл на каждую. Не объединяй несколько обычных frontmatter-блоков в один файл: в стандартном режиме импорта он создаёт одну задачу. Импорт допускает дубликаты и не изменяет уже существующие карточки.

## 5. Примеры хорошего уровня детализации

**Хорошо — ошибка**

- Заголовок: `Исправить потерю порядка карточек после обновления`
- Теги: `project:kanban-tracker, bug`
- Описание: `Проблема: после перезагрузки карточки возвращаются в прежнем порядке. Ожидалось: сохранённый порядок остаётся после обновления страницы. Проверка: изменить порядок и перезагрузить страницу.`

**Хорошо — доработка**

- Заголовок: `Добавить ссылку на инструкцию восстановления`
- Теги: `project:kanban-tracker, docs`
- Описание: `Обновить: раздел резервного копирования в README. Включить: команду восстановления, пример отдельного каталога и предупреждение о перезаписи данных.`

**Плохо**

- `Срочно полностью переработать систему управления проектом, проанализировать архитектуру, улучшить интерфейс и добавить все нужные функции.`
- Причина: слишком много независимых результатов, нет конкретного ожидаемого поведения и непонятно, по каким условиям принимать работу.

## 6. Формат ответа агента

Когда пользователь просит сформировать задачу, по умолчанию верни только:

```text
Заголовок: ...
Теги: project:<slug>, <bug|feature|docs|refactor>
Статус: todo
Описание:
...
```

Если пользователь попросил файл для импорта, верни готовое содержимое одного `.md`-файла с frontmatter. Не добавляй длинных объяснений до или после карточки.
