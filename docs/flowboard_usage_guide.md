# Flowboard: памятка по созданию задач для нескольких проектов

## Главное правило

Flowboard использует одну общую канбан-доску. Проекты разделяются тегами, поэтому у каждой задачи должны быть:

- **один тег проекта** — `project:<slug>`;
- **один тег типа** — `bug`, `feature`, `docs` или `refactor`;
- **короткий заголовок** с конкретным результатом;
- **краткое описание**, достаточное для понимания и проверки задачи.

Одна карточка — один самостоятельный результат. Если в запросе несколько независимых результатов, создай несколько карточек.

## 1. Как выбирать теги

### Тег проекта

Формат: `project:<slug>` — строчные латинские буквы, цифры и дефисы, без пробелов. Используй одно и то же название для проекта во всех задачах.

Примеры:

- `project:storefront` — витрина товаров;
- `project:rope-knots` — Rope Knots;
- `project:template-menu` — меню по дням;
- `project:kanban-tracker` — Flowboard.

Не используй для одного проекта альтернативные варианты вроде `project:storefront` и `storefront`. Если тег нового проекта ещё не согласован, сначала выбери единый короткий slug.

### Тег типа задачи

Выбирай ровно один основной тип:

- `bug` — существующее поведение работает неправильно;
- `feature` — новая возможность или изменение поведения;
- `docs` — документация, инструкции или поясняющие тексты;
- `refactor` — изменение внутренней структуры без изменения поведения пользователя.

При необходимости добавь 1–2 уточняющих тега области, например `frontend`, `backend`, `tests` или `ux`. Не добавляй их автоматически.

**Пример:** `project:storefront, feature, frontend`.

## 2. Как сформулировать заголовок

Хороший заголовок короткий и конкретный: обычно **5–12 слов**, одно действие и один результат. По заголовку должно быть понятно, что нужно исправить или получить.

**Хорошо:**

- `Исправить сброс фильтра после обновления страницы`
- `Добавить ссылку на инструкцию восстановления`
- `Сохранить выбранный проект после перезапуска браузера`

**Плохо:**

- `Улучшить приложение`
- `Разобраться с поиском`
- `Сделать всё удобнее`

Не добавляй `[BUG]` или `[FEATURE]` в заголовок: тип задачи уже обозначен тегом.

## 3. Как написать описание

Обычно достаточно **2–5 коротких строк** или примерно **30–70 слов**. Оставляй только то, что помогает понять проблему или принять результат. Не переписывай историю обсуждения.

### Ошибка — `bug`

```text
Проблема: что происходит сейчас.
Ожидалось: какое поведение должно быть.
Проверка: как убедиться, что исправлено. (если нужно)
```

### Доработка — `feature`

```text
Нужно: какое изменение требуется.
Готово, когда:
- проверяемое условие 1;
- проверяемое условие 2. (если необходимо)
```

### Документация — `docs`

```text
Обновить: конкретный документ или раздел.
Включить: 1–3 обязательных пункта.
```

### Рефакторинг — `refactor`

```text
Область: модуль или компонент.
Изменить: что упростить во внутренней структуре.
Сохранить: поведение или совместимость, которые нельзя нарушить.
```

Не выдумывай причины ошибки, шаги воспроизведения или ожидаемое поведение. Если без недостающего факта задачу нельзя понять, сначала уточни его.

## 4. Создание карточки и статусы

1. Создай карточку через поле быстрого создания над доской и нажми Enter.
2. Открой карточку и добавь тег проекта и тег типа.
3. Вставь краткое описание и при необходимости приложи скриншот, лог или пример входных данных.
4. Перемести задачу в нужную колонку.
5. После проверки результата переведи её в «Готово».

Статусы:

- **К выполнению (`todo`)** — задача сформулирована, но ещё не взята в работу.
- **В работе (`doing`)** — задача выполняется сейчас. По возможности держи здесь не больше 1–3 задач.
- **Ожидает (`waiting`)** — работа заблокирована внешним ответом, решением или зависимостью; укажи причину.
- **Готово (`done`)** — результат проверен и соответствует критериям задачи.

Не используй `waiting` как список идей «на потом» — такие задачи оставляй в `todo`.

## 5. Поиск и просмотр проектов

- Используй тег `project:<slug>`, чтобы отфильтровать задачи нужного проекта.
- Фильтры проекта и обычного тега можно сочетать.
- Поиск учитывает заголовок, описание и теги; все слова поискового запроса должны совпасть. Буквы `ё` и `е` считаются эквивалентными.
- Горячие клавиши: `N` — быстрое создание; `/` или `⌘/Ctrl + K` — поиск; `⌘/Ctrl + Shift + P` — переключение проекта; `?` — справка; `Esc` — закрыть панель.

## 6. Импорт, экспорт и резервные копии

- **Импорт Markdown:** обычный файл с YAML frontmatter создаёт одну задачу. Для набора задач используй отдельный `.md` на каждую задачу.
- **Повторный импорт не ищет дубликаты** и не обновляет существующие карточки — он создаёт новые. Не импортируй один файл повторно без необходимости.
- **Экспорт Markdown** удобен для чтения и переноса текста, но не содержит сами файлы вложений.
- **ZIP-резервная копия** содержит данные задач и вложения. Сохраняй её перед крупными изменениями и регулярно.

Пример файла для импорта:

```markdown
---
title: Исправить сброс фильтра после обновления
status: todo
tags: ["project:kanban-tracker", "bug"]
---
Проблема: выбранный тег сбрасывается после обновления страницы.
Ожидалось: выбранный фильтр остаётся активным.
Проверка: выбрать тег и перезагрузить страницу.
```

## Короткая проверка перед сохранением задачи

- [ ] Заголовок описывает конкретное действие и результат.
- [ ] Указаны один `project:*` и один тег типа.
- [ ] Описание короткое и не содержит догадок.
- [ ] Критерии готовности можно проверить.
- [ ] Независимые результаты вынесены в отдельные карточки.
